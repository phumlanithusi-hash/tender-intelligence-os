## 2026-09-10 — Implementation-time engineering assumptions (Phase 1)

Recorded per build execution §43 — none of these affect security, architecture, data integrity, procurement compliance, major cost, or external service selection, so they were made and logged rather than escalated.

1. **Page-per-domain grouping instead of strict one-file-per-route.** `docs/ARCHITECTURE.md` §4 originally proposed one file per route under `apps/web/src/pages`. During implementation this was consolidated into one file per domain (`tenders.tsx`, `bids.tsx`, `agency.tsx`, `operations.tsx`), each still exporting one distinct component per route. This directly serves the user's Phase 1 instruction not to create unnecessary files, while keeping every route independently testable and named. `docs/ARCHITECTURE.md` §4 should be read with this amendment.
2. **API build tool is tsup (esbuild), not plain `tsc`.** Workspace packages (`@tender-os/constants`, `@tender-os/schemas`, etc.) ship as TypeScript source with no separate compiled output, consumed directly by both `apps/web` (via Vite) and `apps/api`. A plain `tsc` emit for `apps/api` hits the standard monorepo `rootDir` restriction (TS6059) when it needs to include a workspace package's source file that lives outside `apps/api/src`. tsup/esbuild bundles the workspace packages directly into `apps/api/dist/server.js`, sidestepping that restriction without introducing TypeScript project references, which would have added real complexity for no Phase 1 benefit. `tsc --noEmit` remains the source of truth for typechecking.
3. **`@tender-os/schemas` splits client-safe and server-only schemas into separate entry points** (`.` vs `./server` subpath export), rather than one barrel file. A single barrel re-exporting both `clientEnvSchema` and `serverEnvSchema` caused the server schema's field names (e.g. the literal string `SUPABASE_SERVICE_ROLE_KEY`, `OPENAI_API_KEY`) to appear in the compiled frontend bundle, because bundler tree-shaking does not reliably drop unused named exports from a barrel with `export *`. No secret *value* was ever at risk — these were schema field names, not credentials — but shipping them to the browser at all is exactly the boundary blur the user's closing instruction ("the browser must never communicate directly with privileged Supabase operations... SUPABASE_SERVICE_ROLE_KEY must never be exposed to the browser") asks to avoid categorically. Verified fixed: `grep` over the built `apps/web/dist` bundle for `SERVICE_ROLE`, `OPENAI_API_KEY`, and `APIFY_TOKEN` returns no matches after the split.
4. **`@tender-os/types` has no `test` script.** It contains only TypeScript interface declarations with no runtime logic — there is nothing to unit test. Its correctness is verified by `typecheck` instead; this is noted explicitly rather than adding a placeholder test for the sake of having one.
5. **Playwright pinned to 1.56.0, not the initially-scaffolded 1.48.2.** This session's sandbox ships a pre-installed Chromium revision that doesn't match what 1.48.2 expects to download, and outbound download of a matching browser binary is not available. 1.56.0 was chosen because it matches the sandbox's pre-installed Python `playwright` package version, confirming revision compatibility. This is a development-environment detail, not a product decision — either version is fine once a normal (non-sandboxed) CI environment installs its own browsers.
6. **Vite pinned to 5.4.21 in `apps/web`, not 6.x.** Vitest 2.1.4 (current stable at time of writing) depends on Vite 5 internally regardless of the project's own Vite version, and running two major Vite versions side by side in one workspace produced duplicate, incompatible type declarations for `apps/web`'s Vite plugin ecosystem. Pinning to 5.4.21 (the version Vitest already resolves) eliminates the duplication. This can be revisited whenever the project's Vitest version is upgraded to one that supports Vite 6 as a peer.

## 2026-09-10 — Phase 2 schema deviations from the literal field lists

Recorded per build execution §43 — none of these affect the *substance* of the user's data-integrity instructions (no fabricated data, evidence-gated PASS, application-computed scoring, mandatory-failure override, agency isolation); each is a structural addition needed to actually deliver those instructions in a real relational schema, so they were made and logged rather than escalated. Every deviation below is called out in its migration file's own SQL comment as well.

1. **`tender_scores.agency_id` added (not in the Phase 2 §13 literal field list).** An opportunity score is inherently agency-relative — service fit, qualification likelihood, and relevant experience only mean something against one agency's capabilities and evidence. Without `agency_id`, the table could not express "Agency A's score for this tender" separately from "Agency B's score for the same tender," which the master spec's own scoring model requires. Added as `not null references agencies(id)`, consistent with Phase 2 §15's "all agency-owned records must include agency_id" even though tender_scores is not one of the tables §15 explicitly lists.
2. **`tender_risks.agency_id` added, nullable (not in the Phase 2 §14 literal field list).** Some risk types are inherent to the tender itself regardless of who bids (DEADLINE, PRICING, CONTRACT); others are specific to one agency's own situation (CAPACITY, QUALIFICATION). A single not-null agency_id would force every general tender risk to be duplicated per agency or arbitrarily owned by one; a single absent agency_id would prevent agency-specific risk assessments entirely. Nullable resolves this: null = "applies generally, visible to all," a set value = "specific to this agency's own assessment," enforced by the corresponding RLS policy (`tender_risks_select`/`_insert_own_agency`/`_update_own_agency`).
3. **`audit_logs.agency_id` added, nullable (not in the Phase 2 §22 literal field list).** Not every audited action is scoped to one agency (e.g. a source health change touches shared catalogue data with no agency owner), but agency-scoped actions do need agency-scoped visibility under RLS. Nullable follows the same pattern as (2): null = system-wide entry, set = visible only to ADMIN users of that agency (`audit_logs_select_admin_own_agency`).
4. **`tender_requirements` split into `extraction_status` + `qualification_status` (Phase 2 §10 named only one status concept).** The spec's field list names `extraction_status` but separately describes a PASS/FAIL/UNKNOWN/REQUIRES_ACTION status vocabulary for "is this requirement satisfied." These are two genuinely different concerns — did the extraction pipeline succeed in reading this requirement out of a document (`extraction_status`: PENDING/EXTRACTED/FAILED/NEEDS_REVIEW/NOT_APPLICABLE), versus does THIS agency currently satisfy it (`qualification_status`: PASS/FAIL/UNKNOWN/REQUIRES_ACTION/NOT_APPLICABLE, defaulting to UNKNOWN) — and conflating them would make it impossible to distinguish "we haven't extracted this yet" from "we don't currently qualify." The evidence-gating instruction ("do not allow AI to mark a requirement PASS unless there is sufficient agency evidence") is enforced as an actual database CHECK constraint (`tender_requirements_pass_requires_evidence`: `qualification_status <> 'PASS' or qualification_evidence_id is not null`), not left to application-layer discipline alone.
5. **A single polymorphic `agency_evidence` table implements the Phase 2 §17 evidence model, rather than one table per evidence kind.** The spec's TENDER REQUIREMENT → BID SECTION → AGENCY EVIDENCE → GENERATED CLAIM chain needs one normalised place every consumer (a requirement's `qualification_evidence_id`, a bid's `bid_evidence.agency_evidence_id`) can point to regardless of whether the underlying proof is a case study, certificate, document, team member, reference, or policy. `agency_evidence` is polymorphic — exactly one of six nullable FK columns must be set, enforced by `agency_evidence_exactly_one_target` — rather than five-plus loosely related evidence concepts scattered across the schema.
6. **No separate "GENERATED CLAIM" table.** Phase 2 §18 says the bid tables should "establish relationships only," not implement the full bid workflow. The GENERATED CLAIM half of the evidence chain is folded directly into `bid_evidence` as `claim_text` + `verified`, rather than a separate table — the relationship (bid section → evidence → claim) is fully expressible this way, and a dedicated claims table with its own lifecycle is deferred to the phase that actually builds bid generation.
7. **`tender_sources.requires_manual_ingestion` added (not in the Phase 2 §3 literal field list), default `true`.** Phase 2 §3 explicitly says "do not claim these sources are automatically scrapeable yet." A source row with no field distinguishing "has a working adapter" from "is merely known to exist" would make every registered source look equally ingestible from the data alone. Defaulting to `true` and only flipping it once a real adapter ships (Phase 4/5+) keeps that honesty mechanical rather than a documentation-only claim.
8. **`agencies.b_bbee_status` / `agencies.tax_status_status` added (not in the Phase 2 §15 literal field list), typed `evidence_status`.** `b_bbee_level` and `tax_status` are exactly the kind of credential-like claim the master spec's evidence-status vocabulary exists for (§3, §23: "do not allow INFERRED or UNVERIFIED information to silently appear as verified"). Without a paired status column, a claimed B-BBEE level would look identically "true" whether it came from a verified certificate or an unconfirmed onboarding form field. Both default to `UNKNOWN`, the safe value.
9. **`shared/constants` `QUALIFICATION_STATUS` extended with `NOT_APPLICABLE`.** Phase 1 defined this enum (`PASS`, `FAIL`, `UNKNOWN`, `REQUIRES_ACTION`) before the database schema existed. The Phase 2 `qualification_status` Postgres enum needs `NOT_APPLICABLE` for requirements that do not apply to a given tender/agency pairing (e.g. a B-BBEE requirement for an agency exempt from B-BBEE scoring) — extended to keep the shared TypeScript vocabulary and the database enum from drifting apart. No consumer depended on the four-value list at the time of this change.

None of these decisions touch the instructions the user flagged as non-negotiable (nullable-over-fabricated, evidence-gated PASS, application-computed scoring with mandatory-failure override, per-agency RLS isolation, append-only audit log) — each is additive structure in service of enforcing those instructions at the database level rather than only in application code.

## 2026-09-10 — Phase 3 schema/implementation decisions

1. **`watchlist_items` and `saved_filters` are new tables, added because Phase 2's schema had no place to persist either.** Phase 3 §15/§16 explicitly instruct: "If the Phase 2 schema does not yet contain a watchlist table, create the smallest appropriate migration rather than storing watchlist state only in localStorage" and "do not over-engineer this feature." Both tables are the minimum shape needed: `watchlist_items` (agency_id, user_id, tender_id, notes, unique(user_id, tender_id)) and `saved_filters` (agency_id, user_id, name, filter jsonb, unique(user_id, name)). `saved_filters.filter` stores the exact `/api/tenders` query-parameter object opaquely as JSONB rather than one column per filter field, so adding a new `/api/tenders` filter later never requires a saved-filters migration. Both tables are RLS-scoped to `user_id = auth.uid() and agency_id = current_agency_id()` — a user's watchlist and saved filters are private even from same-agency colleagues, which is a stricter isolation boundary than every other Phase 2 table (agency-only) and was verified with a dedicated third-user-same-agency RLS test.
2. **The Tender Radar's list query embeds services/sources/scores via PostgREST resource embedding rather than separate requests per row.** The table's "Services"/"Source"/"Score" columns don't exist on the plain `tenders` table; each row's data comes from `tender_services`, `tender_source_records`, and `tender_scores`. All three are embedded in the single `/api/tenders` query (`repositories/tenders.ts`) — never fetched with a follow-up request per row — to satisfy Phase 3 §21's "Do not fetch the entire database and filter in React. Filtering, sorting and pagination should happen server-side." PostgREST forbids embedding one relation twice in the same query, so filtering-by-relation (`!inner` + an extra column) and always-displaying-that-relation's data use the *same* embed expression, switched conditionally, rather than two separate embeds.
3. **No semantic/vector search in Phase 3, per explicit instruction.** The search field and `search` query parameter exist and are wired end to end (debounced input → `/api/tenders?search=`), but server-side matching is a plain `ilike` scan over title/tender_number/organisation — the frontend interaction and API query architecture Phase 3 asked for, not the semantic/vector search explicitly deferred to a later phase.
4. **E2E authentication is faked entirely client-side; no real Supabase project is used in tests.** `tests/e2e/tender-radar.spec.ts` seeds `localStorage` with the exact session shape `@supabase/supabase-js` reads (`sb-<host-label>-auth-token`, with an `expires_at` far enough in the future that no token-refresh network call is ever triggered), and every `/api/*` call is separately intercepted by Playwright and answered from `tests/e2e/fixtures/tenders.ts` — synthetic, clearly-fake data, never a real or live tender record (Phase 3 §25: "Do not require live tender data for tests. Use controlled test fixtures/mocks."). This requires a *syntactically valid but non-real* `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` to be present so the frontend's `RequireAuth` guard doesn't short-circuit into its "not configured" state — rather than writing `apps/web/.env.local` (which would silently break the existing Phase 1 E2E test asserting the *unconfigured* state), `tests/e2e/playwright.config.ts` now runs two independent dev-server instances side by side: `:5173` with no env (Phase 1's `app-shell.spec.ts` target, still asserting "not configured") and `:5174` started with the fake env injected as process env for that server only (Phase 3's `tender-radar.spec.ts` target). Neither server nor test ever contacts a real Supabase project.

## 2026-09-11 — Phase 4 (Source Registry) decisions

1. **`adapter_state` is a new enum, kept deliberately separate from the existing (Phase 2) `source_health` enum.** They answer different questions — "what did an operator configure" vs. "is it actually working" — and conflating them would make it impossible to represent, say, a correctly-configured ACTIVE adapter that is currently failing (`FAILED` health) vs. an operator-paused adapter (which is not failing, just intentionally off). `source_health` is now computed deterministically from `adapter_state` + active + recent scan outcomes (`apps/api/src/lib/sourceHealth.ts`) rather than being an independently-settable field an operator or adapter could set inconsistently with reality.
2. **`next_scheduled_scan_at` is explicitly NOT a database column.** It is always derivable from `last_scan_at + scan_frequency` (or "now" when never scanned), computed in the API layer (`computeNextScheduledScanAt`) and returned as an API-response-only field. Storing it as a column would create a second value that could silently drift from `last_scan_at`/`scan_frequency` themselves — the smallest-appropriate-migration instruction (Phase 4 §3) argued for deriving it, not storing it.
3. **"Consecutive failed scans" (an input to the health calculation) is derived from `tender_source_scans` on every read, not maintained as a running counter column.** Same reasoning as (2): a stored counter can drift from the scan history it's supposed to summarise (e.g. if a scan row is corrected or deleted); deriving it keeps exactly one source of truth.
4. **Health-check RBAC: restricted to ADMIN, not opened to BID_MANAGER/RESEARCHER.** Phase 4 §18 lists BID_MANAGER/RESEARCHER as able to "view health/history" but does not explicitly say whether they may *trigger* a health check (which writes to `tender_sources.health_status`/`last_success_at`/`last_failure_at`). Since triggering is a write, not a view, and §18's ADMIN row explicitly includes "configure adapters" and "view all operational data," health-check was grouped with the other four write actions (enable/disable/pause/resume) under ADMIN-only, as the more conservative and defensible reading. This can be relaxed later if the product owner wants BID_MANAGER/RESEARCHER to trigger their own health checks.
5. **Read access to the Source Registry (GET endpoints) is NOT further restricted beyond "authenticated" at the RLS layer, only at the application layer.** Phase 4 §18's "Other roles: read-only or no access according to existing RBAC" has no existing precedent in this codebase for a role being denied read access to a shared-catalogue table — every other Phase 2/3 shared table (tenders, services, etc.) is readable by any authenticated user regardless of role. The application layer (`requireRole` with `VIEW_ROLES = [ADMIN, BID_MANAGER, RESEARCHER]`) is the actual gate for GET routes; a VIEWER/WRITER/REVIEWER-role user gets a 403 from the API even though RLS itself would technically permit the read. This keeps RBAC enforcement in one place (the route layer) rather than half in RLS, half in the API.
6. **`GET /api/me` is a new, minimal endpoint**, added because the Source Registry UI needs to know the caller's own role to decide which admin actions to *show* (Phase 4 §18) without duplicating role-resolution logic in the frontend. It is not a general user-profile endpoint — it returns exactly the same `AppUser` shape `middleware/auth.ts` already resolves for every authenticated request.
7. **No notes-editing endpoint was built**, despite Phase 4 §16 saying "Allow appropriate admin notes if the permissions model supports editing." The explicit, required API endpoint list in Phase 4 §19 does not include a notes-update route, and adding one would mean a new PATCH endpoint, a new repository write path, and a new RBAC decision not otherwise called for — over-engineering relative to what was asked (Phase 4's own "do not over-engineer" instructions elsewhere apply by the same spirit here). `notes` is displayed read-only on the Source Detail page's Notes tab; a future phase can add editing if actually needed.
8. **The seed data's aggregator authority level was corrected from `SECONDARY` to `DISCOVERY`.** The Phase 2 seed (`database/seeds/004_tender_sources.sql`) had originally classified EasyTenders/TenderAlerts/TenderBulletins as `SECONDARY` authority. Phase 4 §21 gives an explicit worked example — "EasyTenders … Authority: DISCOVERY, Type: AGGREGATOR" — so this seed was corrected to match the spec's own literal example rather than left inconsistent with it.
9. **Named real issuing entities (Department of Public Works and Infrastructure, City of Johannesburg, City of Cape Town, Eskom, Transnet) were added to the seed alongside the existing category placeholders.** Phase 4 §5 explicitly asks for "issuing government entities, municipalities, SOEs" as primary/authoritative source configurations, not only the generic placeholder rows Phase 2 had. Each new row uses the entity's real public URL (factual reference data) with `active = false`, `adapter_key = null`, no scan history — configuration only, never a claim of connection (Phase 4 §5: "DO NOT claim that they are currently connected").
10. **The Fastify route file `routes/tenderSources.ts` is new, replacing the tender-sources routes that used to live in `routes/catalogue.ts`.** Once the resource grew RBAC-gated administrative actions (enable/disable/pause/resume/health-check) and its own sub-resources (scans, errors, summary), keeping it in the small, deliberately-simple `catalogue.ts` (Phase 3 decision) no longer fit — it now follows the same one-file-per-resource pattern as `routes/tenders.ts` and `routes/watchlist.ts`.

## 2026-09-11 — Phase 5 (eTenders production ingestion) decisions

1. **The discovery mechanism is headless-Chromium (Playwright) DOM scraping of the public listing page, not an API call.** A live-site investigation found the actual opportunities page (`/Home/opportunities`) is a server-rendered shell whose results table is populated client-side after load ("loading, please wait..." with an empty `<tbody>` in the raw HTML) — no documented public API, OCDS feed, or bulk dataset exists. Given the source requires JavaScript execution and no API exists, the least invasive reliable method is rendering the same public page a human visitor sees (no login, no CAPTCHA bypass, no anti-bot circumvention) via the same pre-installed Chromium the E2E suite already uses (`/opt/pw-browsers/chromium`). See `docs/SCRAPING-ARCHITECTURE.md` §12.1.
2. **This build environment's own outbound network access to `etenders.gov.za` is blocked, and this is recorded as an environment limitation, not an eTenders limitation.** Confirmed twice independently: a plain `curl` gets `CONNECT tunnel failed, response 403` from the environment's own egress proxy, and the real adapter's live smoke test (`etenders:smoke`) launches genuine Chromium and fails navigation with `net::ERR_TUNNEL_CONNECTION_FAILED` — the browser-level symptom of the same block. Consequently, the adapter's DOM selectors are a best-effort reconstruction from the page's observed static structure and have never been confirmed against the live rendered DOM from this environment. This is stated here, in `docs/SCRAPING-ARCHITECTURE.md` §12.2, and in the seed data's own source `notes`, deliberately in multiple places, because the user's explicit instruction ("do not manufacture successful live results... report that accurately") is treated as a hard requirement, not a suggestion satisfied by mentioning it once.
3. **`TenderDiscovery` (the shared adapter contract, Phase 4) gained three new OPTIONAL fields: `organisation`, `tenderNumber`, `rawMetadata`.** Phase 4's interface was deliberately minimal (no adapter existed yet to prove what discovery actually needs). Deduplication (Phase 5 §9, primary signal #2 is organisation) and raw-provenance preservation (Phase 5 §6) both genuinely need organisation/tender-number available at discovery time, before a per-tender detail fetch — requiring a detail fetch just to dedupe would multiply request volume against a source with no documented rate-limit tolerance. All three fields are optional, so every Phase 4 fake adapter/test (`registry.test.ts`) is unaffected; this is additive, not a breaking interface change.
4. **A new `IngestionStore` interface (`apps/api/src/lib/ingestion/store.ts`) sits between the generic scan runner and the concrete Supabase-backed repositories, rather than the scan runner calling `SupabaseClient`-based repositories directly.** This sandbox has no running PostgREST endpoint, so a true end-to-end database integration test (Phase 5 §29 explicitly requires one, covering discovery → normalisation → canonical tender → source record → document record → scan history → error history, plus idempotency and partial-failure tests) could not be written against `supabase-js` at all. The seam lets the exact same `runEtendersScan` logic run against a raw-`pg`-backed test implementation of the same interface (`ingestion/__tests__/pgIngestionStore.ts`) talking directly to the real Postgres schema, and against a production Supabase-backed implementation (`ingestion/supabaseIngestionStore.ts`) in the actual API/CLI path — one pipeline, two storage backends, chosen because it was the only way to satisfy §29's real-database requirement in this environment without forking the ingestion logic itself.
5. **Deduplication's "ambiguous" outcome creates a new canonical tender (flagged via a structured `tender_source_errors` row) rather than either auto-merging or failing the record.** Phase 5 §9 requires ambiguous matches to be flagged, not auto-merged — but it does not say what should happen to the incoming record itself. Silently dropping it would violate the "never silently discard" principle; auto-merging with an uncertain candidate risks corrupting an unrelated tender's data via the fill-unknown-fields path (Phase 5 §11: never blindly overwrite). Creating a new tender and recording the ambiguity for human review is the only option that neither loses the record nor risks a wrong merge, at the cost of a possible near-duplicate pair that a reviewer can later reconcile — accepted as the safer failure mode.
6. **Document downloading is explicitly deferred; only discovery (URL/filename/MIME-type-if-determinable) is implemented.** Phase 5 §18 allows deferring downloading when access patterns make it unsafe or unreliable, and explicitly asks for this to be documented rather than silently skipped. Given this environment cannot even validate live discovery (decision 2 above), a "successful download" claim from the same environment would be equally unverifiable — implementing and claiming it here would repeat the same honesty problem the live-access finding already surfaced. `tender_documents` rows are created with `storage_path`/`file_size`/`file_hash`/`downloaded_at` all `null`, meaning exactly "this file was identified," never "this file's content was fetched."
7. **eTenders is seeded at `adapter_state = 'CONFIGURED'`, not `'ACTIVE'`**, despite a real, registered, tested adapter existing. Phase 5 §21 is explicit: "adapter_state = ACTIVE only once the adapter is genuinely operational and validated... Do not set it to ACTIVE before successful validation." Given decision 2, that validation has not happened in this environment — setting `ACTIVE` here would be exactly the fabricated-success claim the user's closing instruction forbids. Moving to `ACTIVE` is left as an explicit deployment-time action (via the Source Registry's existing ADMIN-only "enable" endpoint) for whoever can run `etenders:smoke` from an environment with real network access and see it succeed.
8. **`playwright-core` (not the full `@playwright/test` package) was added as a runtime dependency of `apps/api`**, pinned to the same 1.56.0 version already used by the E2E suite (decision log 2026-09-10 item 5) and pointed at the same pre-installed Chromium binary. `@playwright/test` bundles a full test-runner the API server has no use for; `playwright-core` alone provides the browser-automation API the real transport needs, imported dynamically (`await import('playwright-core')`) so the adapter's pure logic (discovery mapping, normalisation, dedupe) remains importable and unit-testable in any environment, with or without a Chromium binary present.
9. **The manual scan/smoke commands are plain CLI scripts (`apps/api/src/scripts/etendersScan.ts`/`etendersSmoke.ts`) invoked via `tsx`, not new HTTP routes.** Phase 5 §22 asks for "a safe dev/admin command, e.g. `pnpm --filter api etenders:scan`" — a literal script invocation, not an API endpoint. A script run by an operator with access to the server's own environment (and hence its Supabase service-role key) needs no separate authentication step of its own; adding an HTTP route would additionally require session-based auth plumbing for a command that is, by design, run from a trusted server context, not a browser.

## 2026-09-11 — Phase 6 (document ingestion & evidence pipeline) decisions

Full technical detail in `docs/DOCUMENT-INGESTION.md`. This section records the decisions worth escalating-in-writing per build execution §43.

1. **A new shared `apps/api/src/lib/security/urlSafety.ts` module was added rather than extending Phase 5's `adapters/etenders/allowlist.ts` in place.** `allowlist.ts` is a pure, already-tested, narrow domain check (`isAllowedDocumentUrl`) with zero network I/O — extending it in place to add real DNS resolution and private-network rejection would have changed its function signature/behaviour and risked its existing passing test suite (Phase 5 §31). Instead, the new module is a superset capability Phase 5 code could adopt later if desired; `allowlist.ts` itself was not modified and every one of its existing tests still passes unchanged.
2. **`tender_document_processing` is a new table, kept deliberately separate from the existing (Phase 2) `tender_documents.extraction_status` column**, rather than extending that enum with the ~20 fine-grained lifecycle states Phase 6 §2 requires. `extraction_status` (`PENDING/EXTRACTED/FAILED/NEEDS_REVIEW/NOT_APPLICABLE`) is a small, Tender-Detail-facing summary already used by Phase 3's UI and Phase 5's discovery-only writes; overloading it with `DOWNLOAD_QUEUED`/`OCR_PROCESSING`/etc. would have broken that existing, working contract for no benefit — the two concepts (coarse summary vs. fine-grained pipeline state) are genuinely different questions.
3. **A version row (and its processing row) is only created once a download actually succeeds**, rather than optimistically creating a "pending" version before the download is attempted. An optimistic pending-version-per-attempt design would either accumulate orphan rows on every retry (defeating the "no duplicate versions" idempotency requirement, Phase 6 §30) or require additional bookkeeping to reuse a pending row across retries, adding real complexity for a case (first-ever download of a document identity failing) that is already surfaced synchronously in the API response and via logs. Documented as a known limitation in `docs/DOCUMENT-INGESTION.md` §2/§17 rather than silently accepted.
4. **PPTX has no registered extractor.** Phase 6 §33/library-choice instructions explicitly permit choosing `REQUIRES_REVIEW` with a documented limitation over adding "a sketchy dependency just to check a box" when no reasonably-maintained, purely-parsing pure-JS PPTX text extractor exists. None was found; PPTX is detected correctly via magic bytes (so it is never silently misclassified) and routed to `REQUIRES_REVIEW`.
5. **OCR uses the system `tesseract` binary directly (via `child_process`), not the `tesseract.js` npm package.** This sandbox already has a real `tesseract` 5.3.4 binary with the `eng` language pack installed (`tesseract --list-langs`), and `pdftoppm` (poppler-utils) for rasterising scanned PDF pages — both verified working with genuine OCR output and real confidence scores before being built into the pipeline (per the library-choices instruction to "verify each library actually works with a quick smoke test"). `tesseract.js` would need to download its own WASM/language-data assets, an unnecessary extra dependency and network requirement when a working native binary was already present and verified.
6. **`reprocessDocumentVersion()` re-runs the pipeline against the already-stored bytes for a version (fetched back from storage), not against a fresh download of the original URL.** Phase 6 §20 asks to "retry download/extraction/OCR" — but re-fetching from the live web on every reprocess conflates two different operations: "our own extraction pipeline had a bug/transient failure, retry it" (this) versus "check whether the source has published a newer file" (handled by the normal ingestion path creating a new version when the hash differs). Keeping them separate avoids an unnecessary network round-trip (and re-exercising the SSRF-sensitive download path) for what is usually a pure re-processing request.
7. **No new job-queue system was introduced, and BullMQ was confirmed absent first.** `apps/api/package.json` and the whole `apps/api` tree were checked for any existing queue wiring before deciding — none exists (`REDIS_URL` in `.env.example` is an unused placeholder). Per Phase 6 §17's explicit instruction not to build a second queue system, the pipeline is a set of composable, idempotent, retryable, observable stage functions (`processDocument`/`reprocessDocumentVersion`) that a future BullMQ worker will call unchanged; the two mutating API routes call them synchronously only because no queue exists yet, which is the one place this phase knowingly runs pipeline work inside an HTTP handler.
8. **Cross-document (identity-independent) storage deduplication is not implemented.** The deduplication Phase 6 §6 requires is implemented within one document identity (`tender_document_versions` unique on `(document_id, file_hash)`) — the same physical file appearing under two entirely different `tender_documents` rows (e.g. the same generic SBD form attached to two unrelated tenders) is stored twice, once per identity's own deterministic path (Phase 6 §3's own path spec is per-document, not global/content-addressed). A genuinely global, content-addressed store would be a larger architectural change better justified once real duplication volume is observed; documented as a known limitation rather than silently narrowed in scope.
9. **This sandbox's binding network limitation (carried forward from Phase 5) means the download stage's SSRF/redirect/timeout logic is tested against a real, test-owned local HTTP server, never a live external host** — per this phase's own explicit testing instruction ("localhost is reachable within this sandbox for a test-owned server, only external domains are blocked, so this is the correct way to genuinely test the download stage end-to-end"). No live eTenders (or any other live source) document was downloaded, processed, or claimed to have been processed anywhere in this phase's implementation or tests.

## 2026-09-11 — Phase 7 (AI Discovery & Classification) decisions

Full technical detail in `docs/AI-DISCOVERY-CLASSIFICATION.md`. This section records the decisions worth escalating-in-writing per build execution §43.

1. **`api.openai.com` was independently verified unreachable from this sandbox, exactly like `etenders.gov.za` in Phase 5.** A direct `curl` to `https://api.openai.com/v1/models` returns `CONNECT tunnel failed, response 403` from the environment's own egress proxy. No `OPENAI_API_KEY` is configured in this environment either. Both facts are reported honestly rather than worked around: `pnpm ai:smoke` reports `SKIPPED` (not a fabricated `PASS`), and no test in the normal suite depends on live OpenAI access — the `OpenAiClient` port is mocked at the transport boundary everywhere else, per this phase's own binding instruction.
2. **A new `ai_truth_state` enum (`FACT`/`INFERENCE`/`UNKNOWN`/`UNVERIFIED`) was added, deliberately distinct from the existing Phase 2 `evidence_status` enum (`VERIFIED`/`INFERRED`/`UNVERIFIED`/`UNKNOWN`) even though the two vocabularies are close.** `evidence_status` describes the verification state of agency-supplied credential/case-study data (Phase 2 §23); Phase 7's spec explicitly names `FACT`/`INFERENCE`/`UNKNOWN`/`UNVERIFIED` as the AI claim truth-state vocabulary in its own words (§2). Reusing `evidence_status` would have silently conflated two different axes (source-data verification vs. an AI claim's own epistemic status) for a superficial word-count saving; kept separate and documented here and in `docs/AI-ARCHITECTURE.md`'s Phase 7 status note.
3. **Structured, multi-field classification facets (services, geography, contract, briefing) are stored as validated JSONB columns on `tender_ai_classifications` rather than one child table per facet**, while every individual evidence-bearing fact — each JSONB facet as a whole and each deliverable/apparent-requirement item — still gets a fully relational row in `tender_ai_claims`/`tender_ai_evidence`. A literal reading of Phase 7 §19/§20's "conceptually as given in the spec" schema sketch would produce a dozen near-identical narrow tables (one per facet) for data that is always read/written as a unit per classification. The evidence model — the part Phase 7 says is most load-bearing — stays fully relational and FK-enforced regardless; only the facet *values* are grouped. Documented in `docs/AI-DISCOVERY-CLASSIFICATION.md` §11 as the deliberate "adapt, don't blindly copy" call §19 itself invites.
4. **`tender_ai_runs`/`tender_ai_classifications` are agency-scoped (required `agency_id`, RLS-isolated per agency) rather than following the shared-catalogue pattern `tenders` itself uses.** Phase 7 §7 requires relevance to be judged "based on... the agency's configured services" — classification is inherently relative to one agency, not a shared fact about the tender the way its title or closing date is. This mirrors the existing `tender_scores` precedent (Phase 2 decision, `docs/DECISIONS.md` 2026-09-10) for the identical reason. A different agency reclassifying the same tender gets its own independent run/classification history.
5. **No BullMQ (or any other queue) wiring was added; this was re-verified for Phase 7 rather than assumed from Phase 6's finding.** `apps/api/package.json` and the tree were checked again — still no queue dependency, still an unused `REDIS_URL` placeholder. `execution/runAgent.ts` is written as the exact composable, idempotent, retryable, observable stage function a future BullMQ worker would call per job (`ai:tender-classification`), taking no HTTP/Fastify types; the classify/reclassify routes call it fire-and-forget (unawaited, `.catch()`-guarded) so the HTTP response never blocks on the OpenAI round trip, and the run row itself is the pollable progress signal the UI (and a future worker's own status updates) both use.
6. **Idempotency is enforced at the database level (a partial unique index on `tender_ai_runs (tender_id, agency_id) WHERE status IN ('QUEUED','RUNNING')`), not only in application code.** Phase 7 §36 explicitly calls out a race — "calling classify twice rapidly doesn't create two concurrently-running duplicate RUNNING runs" — as a security test target. An application-level "check then insert" has an inherent TOCTOU race under concurrent requests; the database constraint closes it unconditionally, and the application-level check (`findActiveRun`) exists only to fail fast with a friendlier 409 in the common case.
7. **Evidence resolution always discards the model's own `quotedText` and persists only the server-fetched canonical chunk text — there is no "fuzzy match, and if very close then trust it" heuristic.** Phase 7 §17's own worked example ("the server then looks up that exact ID and pulls the real stored text rather than trusting any text the model echoed") reads as a maximally strict standard rather than a similarity-threshold one; implementing a fuzzy-match fallback would reintroduce exactly the "trusting whatever text the model echoed" failure mode the spec identifies by name. A chunk id that resolves is fully trusted for its TEXT (not its truth-state interpretation); a chunk id that doesn't resolve contributes nothing, full stop.
8. **`OPENAI_MODEL` was added to the server env schema (default `gpt-4o-mini`) alongside the pre-existing `OPENAI_API_KEY`/`OPENAI_EMBEDDING_MODEL`.** Phase 7 §3 requires the model to be "configurable, not hard-coded throughout the app"; only `serverEnv.ts`'s default value contains a literal model name, and every call site reads `config.model`.

## 2026-09-11 — Phase 10 (Evaluation & Opportunity Scoring Engine) decisions

Full technical detail in `docs/SCORING-ENGINE.md`.

1. **The spec's literal API paths (`/api/tenders/:id/score...`) collide with a pre-existing, unrelated Phase 3 legacy feature already registered at that exact path** (`routes/tenders.ts`'s `GET /api/tenders/:id/score`, backed by the `tender_scores_risks` table and `BID`/`NO_BID`/`PRIORITY_BID` vocabulary from an earlier phase). Reusing the literal path would either crash Fastify outright (`Method 'GET' already declared for route`, confirmed by trying it) or — worse — silently invite merging two conceptually separate scoring systems, which is explicitly forbidden by this phase's own binding constraints. Every Phase 10 route was therefore moved to `/api/tenders/:id/opportunity-score...` — identical shape/roles/semantics, different base segment — and this deviation is called out in the route file's own header comment, `docs/SCORING-ENGINE.md` §0/§9, and a dedicated E2E test asserting the two paths coexist without colliding.
2. **The pre-existing legacy Phase 3 tab is already labelled "Opportunity Score" in the tender detail UI.** Rather than repurpose or rename that tab (out of scope, and it is a real shipped feature with its own data source), Phase 10's own new tab is labelled **"Scoring Engine"** — the in-page heading still reads "Opportunity score" per the spec's literal UI copy requirement (§39), but the tab label itself is disambiguated so a user is never presented with two tabs claiming the identical name.
3. **`shared/constants/src/scoring.ts` (`SCORING_WEIGHTS`/`SCORE_CLASSIFICATION_BANDS`) — an unused Phase-0 placeholder never wired to any table or route — was deliberately left completely untouched and never imported from.** The binding constraint requires this phase's own weights be "completely conceptually and structurally separate" from any other scoring vocabulary in the system; reusing or renaming that file, even to "clean it up," would risk exactly the confusion the constraint forbids. Phase 10's weights live in a brand-new `shared/constants/src/opportunityScoring.ts` instead.
4. **REQUIREMENT_COVERAGE reuses the already-computed Phase 8 qualification result per requirement, rather than re-evaluating each Phase 9 requirement against agency evidence a second time.** Both phases extend the exact same `tender_requirements` table (Phase 8's `category`/`mandatoryStatus`/rule engine axis and Phase 9's `requirement_type` taxonomy axis coexist on the same row), and Phase 8's `tender_qualification_results.requirement_id` already points at that row. Re-deriving a second, parallel PASS/FAIL classification against the same requirement from the same evidence would risk the two disagreeing over time and would duplicate the entire deterministic rule engine for zero new information. This is the natural, spec-compliant "make requirement coverage a real property of already-verified data" reading, not a shortcut.
5. **A new, minimal, explicit `tender_evaluation_criterion_agency_evidence` link table was added specifically because the spec forbids inventing relevance via semantic matching but requires SOME mechanism for Evaluation Fit to ever be non-UNKNOWN.** No such link concept exists anywhere in Phase 8/9. Rather than skip Evaluation Fit's positive path entirely (which would make it permanently UNKNOWN and therefore never demonstrably testable per the spec's own fixture #1, "strong opportunity"), a deliberately narrow, explicit, non-inferred table was added — populated only by a human/reviewer action or a test fixture, never by any automatic matching logic. No UI/API exists yet to create these links interactively; this is recorded as a known limitation rather than quietly worked around with a semantic shortcut.
6. **Geography (§20) and service alignment (§19) were folded into Strategic Fit and Requirement Coverage respectively as sub-signals, rather than becoming their own top-level dimensions.** The spec's six named dimensions do not include a standalone "Geography" or "Service Alignment" dimension; both concepts are explicitly agency-capability/tender-requirement comparisons that most naturally strengthen or weaken an *existing* named dimension (Strategic Fit for geography — a capacity/capability question; Requirement Coverage for a missing mandatory service — a compliance-gap question) rather than requiring a seventh/eighth dimension and its own weight, which the spec's weight table does not provision for.
7. **CRITICAL_COMPLIANCE_FAILURE is always recorded `OK` in this phase, with no invented trigger condition.** The spec lists it as a named hard gate but gives no distinct example beyond what MANDATORY_QUALIFICATION_FAILURE/MANDATORY_REQUIREMENT_FAILURE already cover with real data. Inventing an arbitrary extra condition (e.g. "any expired certificate") purely so the gate has *something* to check would violate the explicit instruction to "only use information actually available" and to never invent a trigger condition — it is honestly documented as a limitation instead (`docs/SCORING-ENGINE.md` §10).
8. **`tenders.closing_date`/`closing_time` carry no timezone (confirmed by re-reading the Phase 2 schema directly), so `timezoneUnknown` is unconditionally `true` in every scoring run's output**, and a tender closing exactly on today's UTC calendar date is left `OPEN` (not `CLOSED`) rather than guessed either way — the spec explicitly asks for a `TIMEZONE_UNKNOWN` flag rather than a guess, and guessing CLOSED on an ambiguous same-day tender risks incorrectly blocking a still-open, still-biddable opportunity.
9. **The overall score formula renormalises weighted-average contributions over only the KNOWN dimensions' combined weight, rather than dividing by the full configured weight (≈1).** The spec's §21 formula (`Σ(score × weight)`) and its §22 "never silently treat UNKNOWN as 0" instruction are in tension if read as a single un-renormalised sum — an UNKNOWN dimension contributing 0 numerator but its full weight to the denominator IS the "treat UNKNOWN as 0" behaviour the spec forbids. Renormalising by `knownWeight` (documented in full in `docs/SCORING-ENGINE.md` §4) is the reading that satisfies both clauses simultaneously, with `dataCompleteness` reported alongside as the separate, honestly-labelled measure of how much of that renormalised score is actually backed by data.

## 2026-09-11 — Phase 9 (Requirement & Evaluation Extraction) decisions

Full technical detail in `docs/REQUIREMENT-EVALUATION-EXTRACTION.md`.

1. **Extraction is tender-scoped, not agency-scoped, unlike Phase 7 classification and Phase 8 qualification** — requirements and evaluation criteria are properties of the tender's own document set (what the tender actually asks for and how it will be scored), not any one agency's relationship to that tender. This required relaxing `tender_ai_runs.agency_id` from `not null` to nullable and adding a dedicated shared-catalogue RLS policy set plus a new partial unique index (`tender_ai_runs_one_active_per_tender_no_agency`) for the null-agency idempotency case, rather than forcing every extraction run to carry a synthetic or arbitrary agency id it has no real relationship to. The pre-existing per-`(tender_id, agency_id)` index and policies from Phase 7 are untouched.
2. **The existing `requirement_type` enum/column is reused as the Phase 9 taxonomy axis rather than adding a new, parallel `category` column.** Phase 8 already added a separate `category` column to `tender_requirements` for a different purpose — the agency-evidence-check category (`CSD`/`TAX`/`B_BBEE`/`TURNOVER`/`GEOGRAPHIC`/etc.) a requirement maps to for qualification evaluation. Phase 9's taxonomy (`QUALIFICATION`/`FUNCTIONALITY`/`COMMERCIAL`/`PRICE`/`PREFERENCE`/`LOCAL_CONTENT`/`CONTRACTUAL`/`INFORMATIONAL`) answers a genuinely different question — what *kind* of requirement is this in the tender's own structure — so it extends `requirement_type` (already the closest existing concept) instead of overloading Phase 8's `category` or adding a third, confusingly-named column.
3. **`RequirementExtractionAgent` combines what an earlier design sketch (`docs/AI-ARCHITECTURE.md` §3, agents #3/#4) treated as two separate agents (Requirement Extraction, Evaluation Extraction) into a single agent/prompt/call.** Both extractions read the same document chunk context and are naturally produced together by one pass over a tender's documents; running two separate OpenAI calls over the same context would double provider cost and latency for no gain in correctness, since neither extraction depends on the other's *output* (only on the same input). The two output shapes remain fully distinct at the schema and persistence level (`tender_requirements` vs `tender_evaluation_criteria`/`tender_evaluation_gates`) — only the extraction call itself is shared, consistent with the spec's own "reuse the AI infrastructure, do not build a parallel pipeline" instruction.
4. **A requirement's `parent_requirement_id` and a criterion's `parent_criterion_id` are self-referencing foreign keys populated by a two-pass insert-then-link operation, not a single insert with pre-known parent ids.** The model returns hierarchy as array indices ("this item's parent is item 2 in this same response"), and those parent rows do not have real database ids until after they are inserted; a single-pass insert cannot satisfy a self-referencing FK to a row that does not exist yet. The orchestrator therefore inserts every item first (parent link left null), then issues a second update pass wiring each child's `parent_requirement_id`/`parent_criterion_id` to the real id its array-index parent received — never overwriting or reordering the original create.
5. **A conflict proposed by the model is only ever persisted as an actual `CONFLICT` row if the server can independently resolve at least one evidence reference on *both* disagreeing sides; otherwise it is downgraded to `requiresReview` instead of being asserted as a conflict.** The binding instruction is to "produce explicit CONFLICT records when two authoritative documents disagree — never silently pick one," which is a instruction about what to do once a real disagreement between *evidenced* sources is established, not license to persist a conflict the model merely claims exists with no verifiable evidence on one or both sides. Treating an unverifiable claimed conflict as a genuine one would itself be a form of trusting the model's unverified assertion — the same failure mode the evidence-resolution rule elsewhere in this system exists to prevent.
6. **Every numeric evaluation field (`maximumPoints`, `weight`, `minimumThreshold`, `localContentMinPercent`) defaults to `null` in both the raw model-output schema and the persisted row, and a captured scoring `formulaText` is stored as text only, never parsed or executed.** This is the most safety-critical rule in the entire phase per the binding spec ("never invent weights/thresholds/formulas — unspecified → null/UNKNOWN"): the Zod schema for the raw AI output has no field with a numeric default other than `null`, so there is no code path by which an unspecified number could silently become `0` or any other plausible-looking value on its way into the database. A `CHECK` constraint additionally rejects a negative `maximum_points` at the database level, closing the gap even if a future caller bypassed application-level validation.
7. **Re-extraction is append-only and non-destructive: a new extraction run creates entirely new `tender_requirements`/`tender_evaluation_criteria` rows and marks the previous matching rows (by category + normalized title, scoped to rows the agent itself created via `ai_run_id`) as `superseded_by`/`superseded_at`, never updating a historical row's fields in place.** The binding instruction requires "append-only versioning — never overwrite historical extraction," and a human reviewer's prior decision on an earlier version must remain inspectable exactly as it was recorded even after a later re-extraction changes the current view — an in-place `UPDATE` would silently erase that history.
8. **The pre-existing, unguarded Phase 2 baseline `GET /api/tenders/:id/requirements` and `GET /api/tenders/:id/evaluation` routes in `apps/api/src/routes/tenders.ts` were removed and replaced by this phase's role-gated routes at the identical paths, rather than being kept side by side under different paths.** The two implementations returned incompatible response shapes (`{rows: [...]}` of raw DB rows with no role check, versus this phase's `{requirements/criteria, conflicts/gates}` DTO shape with `REQUIREMENT_EVALUATION_VIEW_ROLES` enforcement) at the exact same URL, which crashed Fastify outright ("Method 'GET' already declared for route") rather than merely being redundant. Consolidating onto one, correctly-gated implementation per path — rather than inventing a second path for the old behaviour that nothing was actually using — is a strict improvement (adds RBAC that was previously entirely absent from these two GETs) and was verified not to break any other caller by re-running the full pre-existing API and E2E suites, which required updating four pre-existing E2E fixtures/specs to the new response shape.
8. **Geographic requirements are deliberately never resolved past `UNKNOWN + requiresHumanReview`, per the explicit instruction not to expand the Phase 7 geographic FK-resolution scope.** `AgencyEvidenceSnapshot.geographyText` and `agency_case_studies.geography_text` are plain free-text fields chosen specifically so a later phase could add real province/municipality matching without a schema rewrite — but no such matching logic was written in Phase 8, even though it would have been technically straightforward, because the instruction was explicit that doing so would be scope creep on a known, intentionally-deferred limitation.

4. **The bid-decision engine calls Phase 10's pure `evaluateOpportunity(...)` function directly (via the same `ScoringInput` assembly `lib/scoring/supabaseScoringStore.ts` already builds) rather than requiring a persisted `tender_scoring_runs` row to exist first.** Phase 11 §9 requires consuming Phase 10's `overallScore`/`dataCompleteness`/`gates`/etc.; forcing a caller to separately trigger `/opportunity-score` first (and keep it fresh) before a bid decision could ever be computed would be a confusing, easy-to-forget two-step dependency for what is, underneath, the exact same deterministic computation Phase 10 itself runs before persisting. The live Phase 10 computation is used as the input, and the most recent *persisted* Phase 10 run's id (if one exists) is still recorded on the decision run purely as a citation/reference (`scoring_run_id`), satisfying §39's "the Phase 10 run it was computed from" without inventing a hard dependency Phase 10 itself doesn't impose on its own callers.
5. **Bid policy (`bid_policies`/`bid_policy_versions`) is agency-owned and RLS-scoped per agency, unlike Phase 10's shared-catalogue `scoring_configurations`.** Phase 11 §10/§11 frame bid policy as *this agency's own* business rules (minimum score, excluded sectors, preparation-day thresholds) — a fundamentally per-agency concept, unlike Phase 10's engine configuration (which is a shared, tender-scoring-wide default every agency's opportunity score is computed the same way from). Each agency therefore gets its own seeded 'default' policy row rather than sharing one.
6. **Each threshold field in a bid policy version is stored as a small `{active, severity, value}` JSONB object rather than a bare number/boolean column plus a separate "is this rule on" column.** This directly implements §13/§28 ("only if the policy explicitly configures this rule as active with that severity") as a single self-contained unit per rule — a policy author can never accidentally leave a numeric threshold populated with no way to tell whether it's enforced, and severity travels with its own threshold rather than being tracked in a separate table that could drift out of sync.
7. **The precedence walk (`lib/bidDecision/precedence.ts`) folds severity into decision at each precedence step (`HARD_BLOCK`/`NO_BID` → `NO_BID`, `REVIEW` → `REVIEW`, `WARNING` → never blocking) rather than giving every precedence step a fixed, hard-coded decision.** The literal §7 step list names categories like `MATERIAL_UNRESOLVED_RISK` without specifying whether every such risk is a NO_BID or a REVIEW — that is exactly what §28's four-tier rule severity is for. Reading §7 and §28 together, precedence decides *which* triggered condition is reported as primary; severity (itself entirely policy-configured, never hard-coded) decides whether that primary condition means NO_BID or REVIEW. This is what makes fixture #7b (a low score with NO threshold configured never becoming NO_BID) and test 8 (a low score under a REVIEW-severity policy, distinct from a NO_BID-severity one) both correct under the identical precedence order.
8. **Bid effort (`lib/bidDecision/bidEffort.ts`) is computed from the same live query set the input-assembly layer already gathers (`tender_requirements.mandatory` count, `tender_evaluation_criteria` count/`criterion_type`, `tenders.briefing_required`) — no new extraction/AI step, and no new database columns beyond what Phase 9 already extracts.** §24 is explicit that bid effort must come "ONLY from structured tender characteristics actually available" — inventing new columns or an AI-derived complexity signal would both violate that and duplicate Phase 9's own extraction work for no new information.
9. **Capacity (`capacity: {known: false, ...}`) and expected margin (`minimumExpectedMargin`) are wired all the way through the type system, rule engine, and bid policy schema, but are unconditionally reported `UNKNOWN`/not computed in this phase** — §23 explicitly permits (and the binding constraints require) creating "the schema needed for future capacity integration" without manufacturing data, and §20 forbids ever estimating margin without real cost/pricing data, which does not exist anywhere in this schema. Both are real, typed seams (a `CapacityInput` type, a `minimum_expected_margin` policy column, a permanently-`WARNING`-severity `minimum-expected-margin` rule) rather than TODO comments, so a future phase can wire real data into them without a schema or rule-engine change.
10. **The Phase 11 spec's own worked BID/NO_BID/REVIEW explanation format is followed as a literal string template (`lib/bidDecision/explanations.ts`), not a more "natural-sounding" freeform generator.** §32-§34 give exact example sentences; matching that shape exactly (rather than paraphrasing) keeps the explanation mechanically traceable to the specific rule results that produced it — the same "explainable, not just correct" property the qualification and scoring engines already have.
11. **No dashboard-level Bid Decision filter was added to the Tender Radar table (§55), matching the precedent Phase 10 itself set by not adding one for its own `decisionSignal`.** `apps/web/src/components/tenders/FilterPanel.tsx`/`apps/api/src/routes/tenders.ts` were checked and confirmed to have no Phase 10 filter of this kind either; adding one for Phase 11 alone would require a new join from the tenders list query into `bid_decision_runs` (a query the list endpoint does not currently make for any per-tender run table) purely for this phase, which is disproportionate dashboard/list-query rework for a "minimal addition... if it fits cleanly" instruction that explicitly permits scoping down and documenting why. The per-tender Bid Decision tab is fully functional; a list-level filter is left as a documented gap rather than a half-built one.

## Phase 19 — Production Integration, Data Completeness & Intelligence Operations

1. **The production limitation audit (spec §4) found the two real,
   contained gaps documented in `docs/PRODUCTION-OPERATIONS.md` §1
   (addenda acknowledgement always hard-coded false; no persisted
   data-quality ledger; no aggregate operational-health view) rather
   than a long list of everything imaginable.** Per the spec's own
   "reuse and extend, don't duplicate" instruction, real Supabase
   Storage for tender documents, the Phase 4 source-registry
   operational model, and the Phase 17/18 outcome-provenance/data-
   leakage boundary were all found already correctly implemented and
   were re-verified rather than rebuilt.
2. **Addendum acknowledgement is a new, separate, agency-scoped table
   (`bid_addendum_acknowledgements`), not a column added to the shared
   `tender_addenda` table.** Two different agencies bidding the same
   tender acknowledge its addenda independently — adding acknowledged/
   acknowledged_by columns directly to `tender_addenda` (a shared
   catalogue table with a single `select`-for-`authenticated` RLS
   policy) would have made one agency's acknowledgement visible, and
   overwritable, by every other agency bidding the same tender. The
   new table's materiality is derived, not stored: `isAddendumMaterial`
   (`lib/addenda/reconciliation.ts`) reads the addendum's own confirmed
   `*_changed` flags rather than duplicating that judgement into a new
   column that could drift out of sync.
3. **A material addendum requires acknowledgement; a non-material
   (administrative-only) one never does** — a deterministic, documented
   policy choice (`buildAddendumReconciliationInput`), not an inferred
   one. This closes the Phase 15 Known Limitation
   (`docs/DECISIONS.md` Phase 15 #1) exactly as anticipated there: the
   Phase 15 engine's own `acknowledgementRequired`/`isMaterial`/
   `acknowledged`/`reconciled` fields were already correctly designed
   to receive real data — Phase 19 supplies the real data instead of
   the previous stub.
4. **Five new regression tests
   (`apps/api/src/lib/outcomes/__tests__/historicalIntegrity.test.ts`)
   were added specifically because spec §19 demands dedicated Phase 19
   coverage of the "current score/policy/strategy must never replace
   the at-decision snapshot" property**, not merely a claim that Phase
   17/18's own tests already cover it. No code change was needed in
   `lib/outcomes/learningFeatures.ts` — the structural boundary
   (`assertNoOutcomeLeakage`, the physically separate
   `DecisionTimeFeatures`/`OutcomeFeatures` types) was already correct;
   this entry documents that it was re-verified, not modified.
5. **`data_quality_violations.agency_id` is nullable by design**: a
   rule about shared/catalogue data (e.g. a tender missing its closing
   date) produces a `null`-agency violation visible to every
   authenticated user, exactly mirroring the visibility of the
   underlying `tenders` row it describes; a rule about agency-specific
   data (e.g. a submitted bid with no verified receipt) is scoped to
   that agency. This avoids two failure modes: fabricating an
   arbitrary "owning agency" for a shared-data problem, and hiding an
   agency-specific problem from every other agency by making it
   falsely shared.
6. **The scan never auto-resolves a violation that stops matching a
   candidate on a later run.** Considered and rejected: auto-closing
   would mean the system silently decided a previously-flagged,
   human-facing data problem no longer exists. A human closes a
   violation explicitly (`POST /.../resolve`) with a recorded
   resolution reason — consistent with the "AI/automation is never the
   source of truth for data-quality status" boundary (spec §34).
7. **`GET /api/ops/health` deliberately does not attempt to report
   per-agency source/document/AI figures** — sources, documents, and AI
   runs are shared/catalogue-wide concepts in this schema (mirroring
   `getTenderSourceSummary`, which is likewise not agency-scoped); only
   `outcomes` naturally varies by what an agency can see under RLS, and
   agency-specific breakdowns are already the Data Quality
   completeness dashboard's job, not this endpoint's.
8. **An inaccurate code comment was found and corrected, not
   silently left**: `lib/submissionReadiness/pack.ts` claimed
   `supabaseSubmissionReadinessStore.ts` wires a real Supabase Storage
   adapter for submission packs. No such adapter exists anywhere in
   the codebase. Investigating why revealed the port was never
   actually needed in production: a pack only ever references the
   `storage_path` of files already uploaded through the real,
   already-wired `DocumentStorage` (Phase 6) or `bid_proposal_documents`
   (Phase 14) — never a second upload. The comment now says this
   plainly; the port and its in-memory test adapter are retained,
   correctly labelled as test-only, for a future phase that might need
   to store pack-specific bytes that don't already exist as a document
   row.
